# Проектирование базы данных

Проектирование базы данных – ключевая часть разработки информационных систем. Этап проектирования включает в себя создание структуры хранения данных, определение связей между таблицами, выбор типов данных и методов их обработки.

Для разработки платформы краткосрочной аренды жилья «BelCouch» была спроектирована база данных, которая позволяет хранить, управлять и обрабатывать информацию онлайн-ресурса. База данных «belcouch» состоит из 20 взаимосвязанных таблиц.

Таблица «users» содержит информацию о пользователях сайта. Поля таблицы, их типы, связи и описание представлены в таблице 2.6.

### Таблица 2.6 – Описание таблицы «users»

|------|-----|-------|------------|
| id | int | нет | Уникальный идентификатор (auto_increment) |
| email | varchar(255) | нет | Уникальный email пользователя |
| first_name | varchar(255) | нет | Имя пользователя |
| last_name | varchar(255) | нет | Фамилия пользователя |
| password_hash | varchar(255) | нет | Хеш пароля пользователя |
| password_salt | varchar(255) | нет | Соль для хеширования пароля |
| role | enum('user', 'admin') | нет | Роль пользователя |

## Связи между таблицами

База данных использует следующие основные связи:

1. **users ↔ user_details**: связь один-к-одному (1:1) через поле user_id
2. **users ↔ listings**: связь один-ко-многим (1:N) – один пользователь может иметь несколько объявлений
3. **users ↔ user_ratings**: связь один-ко-многим (1:N) – один пользователь может иметь несколько отзывов
4. **users ↔ messages**: связь один-ко-многим (1:N) – один пользователь может отправлять и получать несколько сообщений
5. **users ↔ favorites**: связь один-ко-многим (1:N) – один пользователь может иметь несколько избранных объявлений
6. **users ↔ verification_requests**: связь один-ко-многим (1:N) – один пользователь может подавать несколько заявок на верификацию
7. **listings ↔ listing_rules**: связь один-ко-многим (1:N) – одно объявление может иметь несколько правил
8. **listings ↔ listing_amenities**: связь один-ко-многим (1:N) – одно объявление может иметь несколько удобств
9. **listings ↔ listing_ratings**: связь один-ко-многим (1:N) – одно объявление может иметь несколько отзывов
10. **listings ↔ listing_reports**: связь один-ко-многим (1:N) – на одно объявление может быть несколько жалоб
11. **listings ↔ messages**: связь один-ко-многим (1:N) – к одному объявлению может относиться несколько сообщений
12. **listings ↔ favorites**: связь один-ко-многим (1:N) – одно объявление может быть в избранном у нескольких пользователей
13. **regions ↔ listings**: связь один-ко-многим (1:N) – в одном регионе может быть несколько объявлений
14. **regions ↔ user_details**: связь один-ко-многим (1:N) – в одном регионе может проживать несколько пользователей
15. **property_types ↔ listings**: связь один-ко-многим (1:N) – один тип жилья может относиться к нескольким объявлениям
16. **stay_durations ↔ listings**: связь один-ко-многим (1:N) – одна длительность проживания может относиться к нескольким объявлениям
17. **rules ↔ listing_rules**: связь один-ко-многим (1:N) – одно правило может относиться к нескольким объявлениям
18. **amenities ↔ listing_amenities**: связь один-ко-многим (1:N) – одно удобство может относиться к нескольким объявлениям
19. **messages ↔ message_attachments**: связь один-ко-многим (1:N) – одно сообщение может иметь несколько вложений

## Вывод

Спроектированная база данных для платформы «BelCouch» обеспечивает эффективное хранение и управление информацией о пользователях, объявлениях жилья, отзывах, сообщениях и других сущностях системы. Нормализованная структура данных с четкими связями между таблицами позволяет выполнять сложные запросы, поддерживать целостность данных и обеспечивать масштабируемость системы. Использование внешних ключей и индексов способствует быстрому поиску и фильтрации данных, что критически важно для работы платформы краткосрочной аренды жилья.
