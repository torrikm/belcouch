# Описание функциональных элементов системы BelCouch

## 1. Регистрация и авторизация

Функции регистрации и авторизации позволяют пользователям создавать учетные записи и входить в систему для доступа к персонализированному функционалу.

Процесс регистрации реализован в файле `api/auth/register.php` через класс `RegisterAction`. Пользователь заполняет форму, вводя email, имя, пароль и подтверждение пароля. Далее данные проходят валидацию: проверяется корректность email, длина пароля (минимум 8 символов), наличие букв и цифр в пароле, совпадение паролей, а также уникальность адреса электронной почты. Если были введены некорректные данные, то выводятся соответствующие сообщения об ошибках. Логика валидации построена по принципу последовательной проверки каждого поля: сначала проверяется заполненность обязательных полей, затем корректность формата email, затем сложность пароля, и наконец совпадение паролей. При обнаружении любой ошибки процесс прерывается и пользователю возвращается массив ошибок с указанием конкретных полей, требующих исправления. Такой подход позволяет пользователю увидеть все ошибки сразу и исправить их за одну попытку.

```php
if ($password === '') {
    $response['errors']['password'] = 'Введите пароль';
} elseif (strlen($password) < 8) {
    $response['errors']['password'] = 'Пароль должен содержать не менее 8 символов';
} elseif (!preg_match('/[0-9]/', $password) || !preg_match('/[a-zA-Z]/', $password)) {
    $response['errors']['password'] = 'Пароль должен содержать буквы и цифры';
}
```

Листинг 1.1 – Валидация пароля при регистрации

Запись новых пользователей в базу данных осуществляется через хеширование пароля с использованием соли и добавления записи в таблицу users. Для обеспечения безопасности паролей используется алгоритм хеширования SHA-256 с уникальной солью для каждого пользователя. Соль генерируется случайно с помощью функции `bin2hex(random_bytes(16))`, что создает 32-символьную шестнадцатеричную строку. Пароль хешируется путем конкатенации исходного пароля и соли, что делает невозможным использование rainbow tables для взлома. После успешного хеширования пароль и соль сохраняются в базе данных, а пользователь сразу получает статус онлайн (is_online = 1), что позволяет системе отслеживать активных пользователей в реальном времени.

```php
$salt = bin2hex(random_bytes(16));
$passwordHash = hash('sha256', $password . $salt);
$db->query("INSERT INTO users (email, first_name, password_hash, password_salt, is_online) VALUES ('$safeEmail', '$safeFirstName', '$passwordHash', '$salt', 1)");
$userId = $db->getLastInsertId();
```

Листинг 1.2 – Хеширование пароля и запись пользователя в базу данных

После успешной регистрации пользователь автоматически авторизуется, его данные сохраняются в сессии. Это реализовано путем записи идентификатора пользователя, email и имени в суперглобальный массив $_SESSION. Сессия используется для поддержания состояния авторизации между различными запросами к серверу. При каждом последующем запросе система проверяет наличие данных в $_SESSION['user_id'] для определения авторизации пользователя. Такой подход позволяет избежать необходимости повторного ввода логина и пароля при переходе между страницами и обеспечивает бесшовный пользовательский опыт.

```php
$_SESSION['user_id'] = $userId;
$_SESSION['user_email'] = $email;
$_SESSION['user_name'] = $firstName;
```

Листинг 1.3 – Сохранение данных пользователя в сессии

Авторизация осуществляется в файле `api/auth/login.php` через класс `LoginAction`. При отправке формы входа происходит проверка заполнения полей, валидация email и сверка введенных данных с базой данных. Пароль проверяется путем хеширования с солью из базы данных. Логика авторизации работает следующим образом: сначала система находит пользователя в базе данных по указанному email, затем извлекает сохраненную соль и хеш пароля, после чего хеширует введенный пароль с той же солью и сравнивает результат с сохраненным хешем. Такое сравнение гарантирует, что даже если база данных будет скомпрометирована, злоумышленники не смогут получить исходные пароли пользователей. При успешной проверке система также обновляет статус пользователя на онлайн, что позволяет другим пользователям видеть, что данный пользователь сейчас активен в системе.

```php
$checkHash = hash('sha256', $password . $user['password_salt']);
if ($checkHash !== $user['password_hash']) {
    $response['errors']['password'] = 'Неверный пароль';
    JsonResponse::send($response);
}
```

Листинг 1.4 – Проверка пароля при авторизации

Если проверка проходит успешно, в сессию помещаются данные пользователя и устанавливается статус онлайн. В сессию сохраняются идентификатор пользователя, email и полное имя (состоит из имени и фамилии через пробел). Эти данные используются для персонализации интерфейса, отображения имени пользователя в меню и других элементах системы. Одновременно выполняется SQL-запрос UPDATE, который устанавливает поле is_online = 1 для данного пользователя, что позволяет системе отслеживать активных пользователей в реальном времени. При выходе из системы или истечении сессии статус онлайн автоматически сбрасывается.

```php
$_SESSION['user_id'] = $user['id'];
$_SESSION['user_email'] = $user['email'];
$_SESSION['user_name'] = $user['first_name'] . ($user['last_name'] ? ' ' . $user['last_name'] : '');
$db->query('UPDATE users SET is_online = 1 WHERE id = ' . (int) $user['id']);
```

Листинг 1.5 – Сохранение данных в сессии и установка статуса онлайн

Также реализован выход пользователя из системы. Для этого используется файл `logout.php`, в котором происходит удаление данных из сессии с помощью `session_unset()`, после чего пользователь считается вышедшим из аккаунта. При выходе также выполняется обновление статуса пользователя в базе данных (is_online = 0), чтобы другие пользователи видели, что данный пользователь больше не активен. Система регистрации и авторизации обеспечивает базовую защиту данных пользователей, поддержку пользовательских сессий и разграничение доступа в зависимости от роли. Все операции с паролями выполняются с использованием криптографически стойких методов хеширования, а валидация на стороне сервера предотвращает инъекции и другие атаки.

## 2. Профиль (личный кабинет)

Функционал личного кабинета позволяет пользователям управлять своими персональными данными, просматривать и редактировать информацию о себе.

Профиль пользователя имеет структурированную организацию с тремя основными разделами: «О себе», «Жилье» и «Избранное». Каждый раздел реализован в отдельном файле в директории `profile/`: `about.php` (о себе), `housing.php` (жилье), `favorites.php` (избранное). Навигация между разделами осуществляется через меню profile-nav, которое отображается на каждой странице профиля. Логика определения владельца профиля реализована через сервис `ProfilePageService`, который сравнивает ID пользователя из сессии с ID профиля из URL-параметра. Переменная `isOwnProfile` определяет, просматривает ли пользователь свой собственный профиль или профиль другого пользователя, что влияет на доступность определенных функций и отображение интерфейса.

```php
$profile_id = isset($_GET['id']) ? intval($_GET['id']) : (isset($_SESSION['user_id']) ? $_SESSION['user_id'] : 0);

if (!isset($_SESSION['user_id']) && $profile_id === 0) {
    header('Location: ' . SITE_URL . 'index#login-modal');
    exit;
}
```

Листинг 2.1 – Проверка авторизации и перенаправление на профиль

Обновление профиля реализовано через класс `UpdateProfileAction` в файле `app/Users/Actions/UpdateProfileAction.php`. Пользователь может изменять имя, фамилию, email, регион, город, пол, дату рождения и загружать аватар. Логика обновления профиля включает несколько уровней проверки безопасности: сначала проверяется авторизация пользователя, затем проверяется, что пользователь пытается редактировать только свой собственный профиль (сравнение ID пользователя из сессии с ID из POST-запроса). После этого выполняется валидация всех обязательных полей и формата email. Особое внимание уделяется верифицированным пользователям – для них запрещено изменение имени и фамилии, чтобы предотвратить мошенничество и подмену личности после прохождения верификации.

```php
if (isset($_FILES['avatar']) && $_FILES['avatar']['error'] === UPLOAD_ERR_OK) {
    $allowedTypes = ['image/jpeg', 'image/png', 'image/jpg'];
    if (!in_array($_FILES['avatar']['type'], $allowedTypes, true)) {
        JsonResponse::send(['success' => false, 'message' => 'Недопустимый тип файла аватара. Разрешены только JPG и PNG.'], 422);
    }

    if ($_FILES['avatar']['size'] > 2 * 1024 * 1024) {
        JsonResponse::send(['success' => false, 'message' => 'Размер файла не должен превышать 2 МБ'], 422);
    }
```

Листинг 2.2 – Валидация загружаемого аватара

Для верифицированных пользователей ограничена возможность изменения имени и фамилии. Это ограничение реализовано путем проверки поля is_verify в таблице users перед сохранением изменений. Если пользователь верифицирован (is_verify = 1), система сравнивает новые значения имени и фамилии с текущими значениями из базы данных. При обнаружении любых различий обновление отклоняется с соответствующим сообщением об ошибке. Такая логика обеспечивает целостность верификационного процесса – после подтверждения личности пользователь не может изменить свои идентификационные данные, что повышает доверие к верифицированным аккаунтам в сообществе.

```php
if ((int) ($currentUserRow['is_verify'] ?? 0) === 1) {
    if ($firstName !== $currentUserRow['first_name'] || $lastName !== $currentUserRow['last_name']) {
        JsonResponse::send(['success' => false, 'message' => 'Изменение имени и фамилии недоступно для верифицированных аккаунтов'], 403);
    }
}
```

Листинг 2.3 – Защита изменения данных для верифицированных пользователей

После успешного обновления данные пользователя обновляются в сессии. Это критически важно для поддержания актуальности интерфейса без необходимости перезагрузки страницы. Система обновляет все связанные переменные сессии: first_name, last_name, email, user_email и user_name (полное имя). Обновление сессии происходит после успешного сохранения данных в базу данных, что гарантирует синхронизацию между сессией и базой данных. Если пользователь загрузил новый аватар, система также возвращает специальный флаг avatar_updated, который позволяет клиентской части обновить отображение аватара без дополнительного запроса к серверу.

```php
$_SESSION['first_name'] = $firstName;
$_SESSION['last_name'] = $lastName;
$_SESSION['email'] = $email;
$_SESSION['user_email'] = $email;
$_SESSION['user_name'] = $firstName . ($lastName ? ' ' . $lastName : '');
```

Листинг 2.4 – Обновление данных в сессии

Система профиля обеспечивает безопасное хранение и редактирование персональных данных пользователей с учетом их верификационного статуса. Все операции с профилем выполняются через подготовленные SQL-запросы для предотвращения SQL-инъекций. Загрузка аватара включает проверку типа файла (разрешены только JPG и PNG), размера файла (максимум 2 МБ) и сохранение изображения непосредственно в базу данных как BLOB-объект. Дополнительная информация о пользователе (регион, город, пол, дата рождения) хранится в отдельной таблице user_details, что позволяет оптимизировать структуру базы данных и ускорить основные запросы к таблице users.

### Раздел «О себе» (about.php)

Раздел «О себе» отображает личную информацию пользователя, включая описание (bio), образование, род деятельности и интересы. Логика этого раздела реализована в файле `profile/about.php` с использованием сервиса `ProfilePageService`. Система загружает данные профиля через метод `getProfileData`, который выполняет сложный SQL-запрос с LEFT JOIN для получения основной информации из таблицы users, дополнительных данных из user_details, региона из regions и среднего рейтинга из подзапроса к таблице user_ratings. Описание пользователя поддерживает многострочный формат с автоматическим разбиением на параграфы через функцию explode("\n"). Для владельца профиля отображается кнопка редактирования, которая открывает модальное окно для изменения информации. Также в этом разделе отображаются отзывы о пользователе (до 3 последних) с возможностью оставить новый отзыв, если текущий пользователь авторизован, не является владельцем профиля и еще не оставлял отзыв.

```php
$profileData = $profileService->getProfileData($profile_id);
$user = $profileData['user'];
$isOwnProfile = $profileData['isOwnProfile'];
$ratings = $profileService->getUserRatings($profile_id);
$can_review = $profileService->canReviewUser($profile_id);
```

Листинг 2.5 – Получение данных для раздела «О себе»

### Раздел «Жилье» (housing.php)

Раздел «Жилье» позволяет пользователям просматривать, добавлять, редактировать и удалять свои объявления о жилье. Логика этого раздела реализована в файле `profile/housing.php` с использованием сервиса `ProfileHousingService`. Метод `getUserListingSummary` загружает данные об объявлениях пользователя, включая основную информацию, изображения, правила, удобства и длительность проживания. Если у пользователя нет объявлений, отображается сообщение с предложением добавить объявление (только для владельца профиля). Для просмотра профиля другим пользователем отображается объявление с рейтингом, кнопкой добавления в избранное и возможностью пожаловаться на объявление (если пользователь еще не отправлял жалобу). Владелец профиля видит кнопки редактирования и удаления объявления, а также может добавить новое объявление через модальное окно с формой, включающей тип жилья, количество спальных мест, город, область, название, время пребывания, примечания, фотографии, правила и удобства.

Создание объявления реализовано через класс `SaveListingAction` в файле `app/Modules/Listings/Actions/SaveListingAction.php`. Логика создания включает валидацию обязательных полей, вставку записи в таблицу listings, сохранение правил и удобств в связующие таблицы, а также загрузку изображений в файловую систему. При создании нового объявления выполняется INSERT-запрос с автоматическим установлением времени создания и обновления. После успешного сохранения система получает ID созданного объявления через getLastInsertId для использования при сохранении связанных данных (правил, удобств, изображений).

```php
$db->prepareAndExecute(
    'INSERT INTO listings (user_id, property_type_id, max_guests, title, notes, stay_duration_id, region_id, city, created_at, updated_at) VALUES (?, ?, ?, ?, ?, ?, ?, ?, NOW(), NOW())',
    'iiissiis',
    [$userId, $propertyTypeId, $maxGuests, $title, $notes, $stayDurationId, $listingRegionId, $listingCity]
);
$listingId = $db->getLastInsertId();
```

Листинг 2.6 – Получение данных для раздела «Жилье»

### Раздел «Избранное» (favorites.php)

Раздел «Избранное» отображает список объявлений, сохраненных пользователем. Критически важно, что этот раздел виден только владельцу профиля – другие пользователи не могут просматривать избранное других пользователей. Логика доступа реализована через проверку переменной `isOwnProfile`: если `isOwnProfile` равно false, ссылка на раздел «Избранное» в навигации профиля не отображается. При попытке прямого доступа к URL `profile/favorites.php?id=OTHER_USER_ID` система перенаправляет пользователя на его собственный профиль избранного. Раздел реализован в файле `profile/favorites.php` с использованием метода `getFavoriteListings` сервиса `ProfilePageService`, который выполняет SQL-запрос с JOIN для получения полной информации об избранных объявлениях, включая данные о владельце, типе жилья, регионе и рейтинге. Для владельца профиля отображается кнопка «Очистить список» для удаления всех избранных объявлений. Если избранных объявлений нет, отображается сообщение с предложением найти жилье (для владельца) или сообщение об отсутствии избранных (при просмотре, хотя этот сценарий невозможен из-за ограничений доступа).

```php
<?php if ($isOwnProfile): ?>
    <a href="./favorites" class="profile-nav-item">Избранное</a>
<?php endif; ?>
```

Листинг 2.7 – Ограничение доступа к разделу «Избранное»

Метод `getFavoriteListings` загружает избранные объявления с определением основного изображения через проверку наличия файла main.jpg в директории объявления или поиск любого изображения с разрешением jpg, jpeg, png, gif. Если изображения не найдены, используется заглушка listing-placeholder.svg. Каждое объявление отображается в виде карточки с возможностью удалить из избранного, открыть чат с владельцем и просмотреть подробную информацию.

## 3. Поиск

Функционал поиска позволяет пользователям находить объявления жилья по названию или городу.

Поиск реализован в файле `api/search_listings.php` через сервис `ListingsApiService`. При вводе поискового запроса система выполняет поиск по полям title и city в таблице listings. Логика поиска работает следующим образом: сначала система проверяет, что поисковый запрос не пустой. Если запрос пустой, возвращается пустой массив результатов. При наличии запроса система выполняет SQL-запрос с оператором LIKE, который ищет совпадения в начале, середине или конце строки в полях title и city. Использование оператора LIKE с символами процента (%) позволяет выполнять частичное совпадение – например, запрос "Мин" найдет объявления с названиями "Минск", "Минский район" и т.д. Результаты ограничены до 3 записей для быстрого отображения в автодополнении поиска.

```php
$query = isset($_GET['query']) ? trim($_GET['query']) : '';
if ($query === '') {
    JsonResponse::send(['success' => true, 'results' => []]);
}

$listingsApiService = new ListingsApiService();
$listings = $listingsApiService->getSearchListings($query);
```

Листинг 3.1 – Обработка поискового запроса

Метод `getSearchListings` в классе `ListingsApiService` выполняет SQL-запрос с использованием оператора LIKE для поиска совпадений:

```php
public function getSearchListings(string $query): array
{
    $sql = 'SELECT l.id, l.title, l.city, u.id as user_id, pt.name as property_type FROM listings l JOIN users u ON l.user_id = u.id JOIN property_types pt ON l.property_type_id = pt.id WHERE l.title LIKE ? OR l.city LIKE ? LIMIT 3';
    $stmt = $this->db->prepareAndExecute($sql, 'ss', ["%$query%", "%$query%"]);
    $result = $stmt->get_result();
    $listings = [];

    while ($row = $result->fetch_assoc()) {
        $row['image'] = $this->resolveListingImage((int) $row['id']);
        $listings[] = $row;
    }

    return $listings;
}
```

Листинг 3.2 – Поиск объявлений в базе данных

Система поиска возвращает до 3 результатов с изображениями, что позволяет пользователям быстро находить нужные варианты жилья. Для каждого найденного объявления система дополнительно выполняет метод resolveListingImage, который определяет путь к основному изображению объявления. Логика этого метода проверяет наличие файла main.jpg в директории объявления, затем ищет любые изображения с расширениями jpg, jpeg, png, gif, и если изображения не найдены, возвращает путь к изображению-заполнителю. Такой подход обеспечивает корректное отображение карточек объявлений даже при отсутствии загруженных изображений. Поиск также возвращает информацию о владельце объявления и типе недвижимости, что позволяет пользователям быстро оценить релевантность результатов.

## 4. Фильтрация

Функционал фильтрации позволяет пользователям уточнять поиск объявлений по различным критериям: тип жилья, количество гостей, длительность проживания, регион, город, удобства и правила.

Фильтрация реализована в файле `api/get_filtered_listings.php` через метод `getFilteredListingsData` класса `ListingsApiService`. Система принимает параметры фильтрации через POST-запрос и строит динамический SQL-запрос. Логика фильтрации построена на модульном принципе: сначала все входные параметры преобразуются в структурированный массив фильтров через метод resolveFilters, который приводит типы данных и устанавливает значения по умолчанию для отсутствующих параметров. Затем метод buildWhereClause динамически строит SQL-условие WHERE, добавляя только те условия, для которых указаны значения фильтров. Такой подход позволяет оптимизировать SQL-запросы – если пользователь не указал определенный фильтр, соответствующее условие не добавляется в запрос, что улучшает производительность.

```php
$filters = $this->resolveFilters($input);
$whereData = $this->buildWhereClause($filters);
```

Листинг 4.1 – Разрешение фильтров и построение WHERE-условия

Метод `resolveFilters` преобразует входные данные в структурированный массив фильтров. Этот метод выполняет приведение типов и проверку наличия параметров в массиве input. Для числовых параметров (property_type_id, min_guests, max_guests, stay_duration_id, region_id) используется приведение к типу int с установкой значения 0 по умолчанию. Для строкового параметра city выполняется обрезка пробелов и установка пустой строки по умолчанию. Для массивных параметров (amenities, rules) проверяется, что значение является массивом, иначе устанавливается пустой массив. Такая нормализация данных обеспечивает предсказуемое поведение системы независимо от того, какие параметры были переданы в запросе.

```php
private function resolveFilters(array $input): array
{
    return [
        'property_type_id' => isset($input['property_type']) ? (int) $input['property_type'] : 0,
        'min_guests' => isset($input['min_guests']) ? (int) $input['min_guests'] : 0,
        'max_guests' => isset($input['max_guests']) ? (int) $input['max_guests'] : 0,
        'stay_duration_id' => isset($input['stay_duration']) ? (int) $input['stay_duration'] : 0,
        'region_id' => isset($input['region']) ? (int) $input['region'] : 0,
        'city' => isset($input['city']) ? trim((string) $input['city']) : '',
        'has_amenities' => isset($input['amenities']) && is_array($input['amenities']) ? $input['amenities'] : [],
        'has_rules' => isset($input['rules']) && is_array($input['rules']) ? $input['rules'] : [],
    ];
}
```

Листинг 4.2 – Разрешение параметров фильтрации

Метод `buildWhereClause` динамически строит SQL-условие на основе активных фильтров. Логика этого метода перебирает все фильтры и добавляет соответствующие SQL-условия в массив conditions. Для каждого условия также добавляется значение параметра в массив params и указывается тип данных в строке types (i для integer, s для string). Для числовых диапазонов (min_guests, max_guests) используются операторы сравнения >= и <=. Для текстового поиска по городу используется оператор LIKE с символами процента для частичного совпадения. Для фильтрации по удобствам и правилам используются подзапросы EXISTS, которые проверяют наличие соответствующих записей в связующих таблицах listing_amenities и listing_rules. Все условия объединяются оператором AND, что означает, что должны выполняться все указанные фильтры одновременно.

```php
if ($filters['property_type_id'] > 0) {
    $conditions[] = 'l.property_type_id = ?';
    $params[] = $filters['property_type_id'];
    $types .= 'i';
}
if ($filters['min_guests'] > 0) {
    $conditions[] = 'l.max_guests >= ?';
    $params[] = $filters['min_guests'];
    $types .= 'i';
}
if ($filters['city'] !== '') {
    $conditions[] = 'l.city LIKE ?';
    $params[] = '%' . $filters['city'] . '%';
    $types .= 's';
}
```

Листинг 4.3 – Построение условий фильтрации

Для удобств и правил используются подзапросы EXISTS. Это необходимо, так как удобства и правила хранятся в отдельных таблицах с отношением «многие-ко-многим» к объявлениям. Подзапрос EXISTS проверяет наличие хотя бы одной записи в связующей таблице для данного объявления и указанного удобства/правила. При выборе нескольких удобств или правил условия объединяются оператором AND, что означает, что объявление должно иметь ВСЕ выбранные удобства или правила. Например, если пользователь выбрал удобства «Wi-Fi» и «Парковка», система найдет только те объявления, у которых есть оба этих удобства. Такой подход обеспечивает точную фильтрацию по множественным критериям.

```php
if (!empty($filters['has_amenities'])) {
    $amenityConditions = [];
    foreach ($filters['has_amenities'] as $amenityId) {
        $amenityId = (int) $amenityId;
        if ($amenityId > 0) {
            $amenityConditions[] = 'EXISTS (SELECT 1 FROM listing_amenities la WHERE la.listing_id = l.id AND la.amenity_id = ?)';
            $params[] = $amenityId;
            $types .= 'i';
        }
    }
    if (!empty($amenityConditions)) {
        $conditions[] = '(' . implode(' AND ', $amenityConditions) . ')';
    }
}
```

Листинг 4.4 – Фильтрация по удобствам

Система также поддерживает пагинацию результатов и проверку избранного для авторизованных пользователей. Пагинация реализована через параметры page (текущая страница) и perPage (количество записей на страницу, фиксировано 12). Система вычисляет смещение (offset) для SQL-запроса по формуле (page - 1) * perPage и общее количество страниц по формуле ceil(totalListings / perPage). Для авторизованных пользователей система дополнительно получает список ID избранных объявлений через метод getUserFavoriteIds, что позволяет отметить избранные объявления в интерфейсе. При рендеринге HTML-кода система проверяет, находится ли ID текущего объявления в массиве избранных, и добавляет соответствующий класс или иконку для визуального обозначения избранного статуса.

```php
$userFavorites = $viewerId ? $this->getUserFavoriteIds($viewerId) : [];
$totalListings = $this->getTotalListings($whereData);
$totalPages = (int) ceil($totalListings / $perPage);
$listings = $this->getListings($whereData, $offset, $perPage);
```

Листинг 4.5 – Получение результатов с пагинацией

Система фильтрации обеспечивает гибкий и мощный поиск объявлений с поддержкой множественных критериев и пагинации. Динамическое построение SQL-запросов позволяет системе адаптироваться к любому набору фильтров без необходимости написания отдельных запросов для каждой комбинации. Использование подготовленных запросов с параметризованными значениями защищает от SQL-инъекций. Пагинация позволяет эффективно обрабатывать большие объемы данных, загружая только нужную порцию записей. Интеграция с системой избранного обеспечивает персонализированный опыт для авторизованных пользователей, позволяя им быстро находить сохраненные объявления среди результатов фильтрации.

## 5. Отзывы о пользователе

Функционал отзывов о пользователях позволяет оставлять оценки и комментарии о других пользователях системы после взаимодействия.

Отправка отзыва о пользователе реализована через класс `SubmitUserReviewAction` в файле `app/Reviews/Actions/SubmitUserReviewAction.php`. Пользователь может оценить другого пользователя от 1 до 5 баллов и оставить текстовый комментарий. Логика отправки отзыва включает строгую валидацию входных данных: проверяется, что ID оцениваемого пользователя и ID оценивающего пользователя положительные, оценка находится в диапазоне от 1 до 5, а комментарий не пустой. Такая валидация предотвращает отправку некорректных или неполных отзывов. Система не ограничивает количество отзывов от одного пользователя к другому, что позволяет пользователям обновлять свои оценки после повторных взаимодействий.

```php
$userId = isset($_POST['user_id']) ? (int) $_POST['user_id'] : 0;
$raterId = (int) $_SESSION['user_id'];
$comment = trim($_POST['comment'] ?? '');
$rating = (int) ($_POST['rating'] ?? 0);

if ($userId <= 0 || $raterId <= 0 || $rating < 1 || $rating > 5 || $comment === '') {

```

Листинг 5.1 – Валидация данных отзыва

Отзыв сохраняется в таблицу `user_ratings` с указанием ID пользователя, ID оценивающего, комментария, оценки и даты создания. Использование отдельной таблицы для отзывов позволяет эффективно хранить историю всех оценок и выполнять аналитические запросы. Дата создания автоматически устанавливается функцией NOW() базы данных, что гарантирует точность временной метки. После сохранения отзыва система немедленно пересчитывает средний рейтинг оцениваемого пользователя, используя SQL-функцию AVG для вычисления среднего арифметического всех оценок. Функция COALESCE используется для возврата 0 вместо NULL, если у пользователя еще нет отзывов.

```php
$stmt = $db->prepareAndExecute(

    'iisi',
    [$userId, $raterId, $comment, $rating]

```

Листинг 5.2 – Сохранение отзыва в базу данных

После сохранения отзыва система пересчитывает средний рейтинг пользователя. Пересчет происходит в реальном времени при каждом добавлении нового отзыва, что обеспечивает актуальность рейтинга. Система также подсчитывает общее количество отзывов (rating_count), которое используется для отображения статистики и оценки надежности рейтинга (большее количество отзывов указывает на более надежную оценку). Средний рейтинг округляется до одного десятичного знака при хранении в базе данных, что обеспечивает консистентное отображение рейтинга во всех частях системы.

```php
$ratingStmt = $db->prepareAndExecute(
    'SELECT COALESCE(AVG(rating), 0) AS avg_rating, COUNT(*) AS rating_count FROM user_ratings WHERE user_id = ?',
    'i',
    [$userId]
);
$ratingData = $ratingStmt->get_result()->fetch_assoc();
$avgRating = isset($ratingData['avg_rating']) ? (float) $ratingData['avg_rating'] : 0.0;
$ratingCount = isset($ratingData['rating_count']) ? (int) $ratingData['rating_count'] : 0;
```

Листинг 5.3 – Пересчет среднего рейтинга пользователя

Система возвращает информацию о созданном отзыве, включая данные об авторе отзыва. Клиентская часть получает полный объект отзыва с ID, данными об авторе (имя, фамилия, наличие аватара), текстом комментария, оценкой и датой создания. Также возвращается обновленный средний рейтинг и количество отзывов оцениваемого пользователя, что позволяет интерфейсу немедленно отобразить изменения без дополнительного запроса. Такой подход обеспечивает мгновенную обратную связь для пользователя и актуальность отображаемой информации.

```php
$userStmt = $db->prepareAndExecute(
    'SELECT first_name, last_name, avatar_image FROM users WHERE id = ?',

$userData = $userStmt->get_result()->fetch_assoc();

JsonResponse::send([

Листинг 5.4 – Возврат данных о созданном отзыве

Система отзывов о пользователях обеспечивает прозрачность и доверие в сообществе через систему оценок и комментариев. ## 6. Отзывы о жилье

Функционал отзывов о жилье позволяет пользователям оценивать качество проживания в конкретных объявлениях.

Отправка отзыва о жилье реализована через класс `SubmitListingReviewAction` в файле `app/Reviews/Actions/SubmitListingReviewAction.php`. Пользователь может оценить объявление от 1 до 5 баллов и оставить текстовый комментарий. Логика отзывов о жилье включает дополнительные проверки по сравнению с отзывами о пользователях: система проверяет, что пользователь не оставлял ранее отзыв на это же объявление (запрет повторных отзывов), и что пользователь не является владельцем оцениваемого объявления (запрет самооценки). Эти ограничения обеспечивают честность и объективность отзывов, предотвращая накрутку рейтинга и фальсификацию отзывов.

```php
$listingId = isset($_POST['listing_id']) ? (int) $_POST['listing_id'] : 0;
$rating = isset($_POST['rating']) ? (int) $_POST['rating'] : 0;
$comment = trim($_POST['comment'] ?? '');

if ($listingId <= 0) {
    JsonResponse::send(['success' => false, 'message' => 'ID объявления указано неверно'], 422);

Листинг 6.1 – Валидация данных отзыва о жилье

Система проверяет, что пользователь не оставлял ранее отзыв на это объявление и не является владельцем оцениваемого объявления. Проверка уникальности отзыва выполняется через SQL-запрос, который ищет существующую запись в таблице listing_ratings с тем же listing_id и user_id. Если запись найдена, система возвращает ошибку с сообщением о том, что отзыв уже был оставлен. Проверка запрета самооценки выполняется путем сравнения user_id владельца объявления с ID текущего пользователя. Эти проверки критически важны для поддержания целостности системы отзывов и предотвращения манипуляций рейтингами.

```php
$checkStmt = $db->prepareAndExecute('SELECT id FROM listing_ratings WHERE listing_id = ? AND user_id = ?', 'ii', [$listingId, $userId]);
if ($checkStmt->get_result()->num_rows > 0) {
    JsonResponse::send(['success' => false, 'message' => 'Вы уже оставляли отзыв на это объявление'], 422);
}

$listing = $listingResult->fetch_assoc();
if ((int) $listing['user_id'] === $userId) {

```

Листинг 6.2 – Проверка уникальности отзыва и запрета самооценки

Отзыв сохраняется в таблицу `listing_ratings`. Таблица хранит связь между объявлением, пользователем, оставившим отзыв, текстом комментария, оценкой и датой создания. Использование отдельной таблицы позволяет эффективно выполнять аналитические запросы и поддерживать историю всех отзывов. После сохранения отзыва система автоматически обновляет поле avg_rating в таблице listings, выполняя подзапрос для вычисления среднего значения всех оценок для данного объявления. Это позволяет быстро получать рейтинг объявления без необходимости выполнения JOIN с таблицей отзывов при каждом отображении.

```php
$stmt = $db->prepareAndExecute('INSERT INTO listing_ratings (listing_id, user_id, comment, rating) VALUES (?, ?, ?, ?)', 'iisi', [$listingId, $userId, $comment, $rating]);
```

Листинг 6.3 – Сохранение отзыва о жилье

После сохранения система обновляет средний рейтинг объявления. Обновление выполняется через SQL-запрос UPDATE с подзапросом, который вычисляет AVG(rating) для всех отзывов данного объявления. Такой подход гарантирует, что рейтинг всегда актуален и отражает все оставленные отзывы. Система также возвращает обновленное значение среднего рейтинга в ответе клиенту, что позволяет немедленно обновить отображение рейтинга в интерфейсе без дополнительного запроса. Рейтинг хранится как число с плавающей точкой, что позволяет отображать дробные значения (например, 4.5 из 5).

```php
$db->prepareAndExecute('UPDATE listings SET avg_rating = (SELECT AVG(rating) FROM listing_ratings WHERE listing_id = ?) WHERE id = ?', 'ii', [$listingId, $listingId]);

$avgStmt = $db->prepareAndExecute('SELECT AVG(rating) AS avg_rating FROM listing_ratings WHERE listing_id = ?', 'i', [$listingId]);

```

Листинг 6.4 – Обновление среднего рейтинга объявления

Система отзывов о жилье помогает пользователям делать обоснованный выбор при бронировании на основе опыта других пользователей. Ограничение на один отзыв от пользователя на объявление обеспечивает разнообразие мнений и предотвращает доминирование одного пользователя в рейтинге. Запрет самооценки гарантирует объективность отзывов. Автоматический пересчет рейтинга обеспечивает актуальность информации, а хранение полной истории отзывов позволяет пользователям читать подробные комментарии и принимать взвешенные решения. Система рейтинга жилья является ключевым фактором доверия в платформе краткосрочной аренды.

## 7. Рейтинг пользователя

Рейтинг пользователя рассчитывается как среднее арифметическое всех оценок, полученных от других пользователей через систему отзывов.

Расчет рейтинга пользователя выполняется автоматически при каждом добавлении нового отзыва. Система использует SQL-функцию AVG для вычисления среднего значения. Логика расчета рейтинга работает следующим образом: при добавлении нового отзыва система выполняет запрос SELECT AVG(rating) FROM user_ratings WHERE user_id = ?, который возвращает среднее арифметическое всех оценок для данного пользователя. Функция COALESCE используется для возврата 0 вместо NULL, если у пользователя еще нет отзывов. Такой подход гарантирует, что рейтинг всегда имеет числовое значение и может быть корректно отображен в интерфейсе.

```php
$ratingStmt = $db->prepareAndExecute(
    'SELECT COALESCE(AVG(rating), 0) AS avg_rating, COUNT(*) AS rating_count FROM user_ratings WHERE user_id = ?',
    'i',
    [$userId]
);
$ratingData = $ratingStmt->get_result()->fetch_assoc();
$avgRating = isset($ratingData['avg_rating']) ? (float) $ratingData['avg_rating'] : 0.0;
$ratingCount = isset($ratingData['rating_count']) ? (int) $ratingData['rating_count'] : 0;
```

Листинг 7.1 – Расчет среднего рейтинга пользователя

Рейтинг пользователя также учитывается при отображении объявлений. В запросе `getListings` класса `ListingsApiService` выполняется LEFT JOIN с подзапросом для получения рейтинга владельца. Подзапрос группирует отзывы по user_id и вычисляет AVG(rating) для каждого пользователя. LEFT JOIN используется вместо INNER JOIN, чтобы объявления отображались даже если у владельца еще нет отзывов (в этом случае рейтинг будет 0). Такой подход позволяет пользователям видеть рейтинг хозяина при просмотре объявления, что помогает оценить надежность и качество обслуживания. Рейтинг владельца является важным фактором при принятии решения о бронировании.

```php
$sql = "SELECT l.*, pt.name as property_type_name, r.name as region_name, sd.name as stay_duration_name, u.first_name, u.last_name, COALESCE(ur.avg_rating, 0) as user_rating, u.avatar_image, u.is_verify FROM listings l JOIN property_types pt ON l.property_type_id = pt.id JOIN regions r ON l.region_id = r.id LEFT JOIN stay_durations sd ON l.stay_duration_id = sd.id JOIN users u ON l.user_id = u.id LEFT JOIN (SELECT user_id, AVG(rating) as avg_rating FROM user_ratings GROUP BY user_id) ur ON ur.user_id = u.id {$whereData['where_clause']} ORDER BY l.created_at DESC LIMIT {$offset}, {$perPage}";
```

Листинг 7.2 – Получение рейтинга пользователя при выборке объявлений

Система рейтинга пользователей обеспечивает прозрачность и помогает другим пользователям оценивать надежность хозяев жилья. Публичное отображение рейтинга создает стимул для пользователей поддерживать высокое качество обслуживания и честность в взаимодействиях. Система не реализует механизмы взвешивания отзывов (например, более свежие отзывы имеют больший вес), что обеспечивает простоту и прозрачность расчета рейтинга. Рейтинг обновляется в реальном времени, что обеспечивает актуальность информации. Количество отзывов также отображается в системе, позволяя пользователям оценивать статистическую значимость рейтинга.

## 8. Рейтинг жилья

Рейтинг жилья рассчитывается как среднее арифметическое всех оценок, полученных конкретным объявлением от пользователей.

При добавлении отзыва о жилье система автоматически пересчитывает средний рейтинг объявления. Логика обновления рейтинга использует SQL-подзапрос внутри UPDATE-запроса: UPDATE listings SET avg_rating = (SELECT AVG(rating) FROM listing_ratings WHERE listing_id = ?) WHERE id = ?. Такой подход гарантирует, что рейтинг всегда отражает все оставленные отзывы и автоматически обновляется при каждом новом отзыве. Рейтинг хранится в поле avg_rating таблицы listings, что позволяет быстро получать значение рейтинга без выполнения JOIN операций при отображении карточек объявлений.

```php
$db->prepareAndExecute('UPDATE listings SET avg_rating = (SELECT AVG(rating) FROM listing_ratings WHERE listing_id = ?) WHERE id = ?', 'ii', [$listingId, $listingId]);

$avgStmt = $db->prepareAndExecute('SELECT AVG(rating) AS avg_rating FROM listing_ratings WHERE listing_id = ?', 'i', [$listingId]);
$avgResult = $avgStmt->get_result()->fetch_assoc();
$avgRating = isset($avgResult['avg_rating']) ? (float) $avgResult['avg_rating'] : 0.0;
```

Листинг 8.1 – Обновление рейтинга объявления

Рейтинг объявления хранится в поле `avg_rating` таблицы `listings` и отображается на карточках объявлений. Это позволяет пользователям быстро оценивать качество жилья на основе отзывов других пользователей. Рейтинг отображается в виде числового значения (обычно с одним десятичным знаком) и часто сопровождается визуальным отображением в виде звезд или других индикаторов. Система также позволяет сортировать объявления по рейтингу, что помогает пользователям находить наиболее популярные и качественные варианты жилья. Рейтинг жилья является ключевым фактором при принятии решения о бронировании и влияет на видимость объявления в поиске.

## 9. Избранное

Функционал избранного позволяет пользователям сохранять интересные объявления в личный список для быстрого доступа в будущем.

Добавление и удаление из избранного реализовано через класс `ToggleFavoriteAction` в файле `app/Favorites/Actions/ToggleFavoriteAction.php`. Система проверяет, находится ли объявление уже в избранном, и выполняет соответствующее действие. Логика работы системы избранного построена по принципу переключателя (toggle): сначала выполняется запрос SELECT для проверки наличия записи в таблице favorites с данным user_id и listing_id. Если запись найдена, она удаляется (DELETE), и система возвращает действие 'removed'. Если запись не найдена, создается новая запись (INSERT) с текущей датой и временем, и система возвращает действие 'added'. Такой подход позволяет использовать одну конечную точку API для обеих операций.

```php
$checkStmt = $db->prepareAndExecute('SELECT id FROM favorites WHERE user_id = ? AND listing_id = ?', 'ii', [$userId, $listingId]);
$favorite = $checkStmt->get_result()->fetch_assoc();

if ($favorite) {
    $db->prepareAndExecute('DELETE FROM favorites WHERE id = ?', 'i', [(int) $favorite['id']]);
    JsonResponse::send([
        'success' => true,
        'action' => 'removed',
        'message' => 'Объявление удалено из избранного'
    ]);
}

$createdAt = date('Y-m-d H:i:s');
$db->prepareAndExecute('INSERT INTO favorites (user_id, listing_id, created_at) VALUES (?, ?, ?)', 'iis', [$userId, $listingId, $createdAt]);
```

Листинг 9.1 – Переключение статуса избранного

При фильтрации объявлений система также проверяет, находится ли объявление в избранном у авторизованного пользователя. Это реализовано через предварительную загрузку списка ID избранных объявлений для текущего пользователя. Метод getUserFavoriteIds выполняет запрос SELECT listing_id FROM favorites WHERE user_id = ? и возвращает массив ID. Этот массив затем используется при рендеринге каждой карточки объявления для проверки, находится ли ID текущего объявления в массиве избранного. Такой подход позволяет отметить избранные объявления визуально (например, иконкой сердца) без необходимости выполнения отдельного запроса для каждого объявления.

```php
$userFavorites = $viewerId ? $this->getUserFavoriteIds($viewerId) : [];
```

Листинг 9.2 – Получение списка избранного пользователя

Метод `getUserFavoriteIds` возвращает массив ID объявлений, добавленных в избранное. Метод выполняет простой SQL-запрос и итерирует по результатам, формируя массив целых чисел. Использование массива ID вместо загрузки полных данных об объявлениях оптимизирует производительность и уменьшает объем передаваемых данных. Метод возвращает пустой массив для неавторизованных пользователей или если пользователь еще не добавил ни одного объявления в избранное. Такая логика позволяет единообразно обрабатывать случаи с отсутствием избранного без дополнительных проверок на null.

```php
private function getUserFavoriteIds(int $userId): array
{
    $stmt = $this->db->prepareAndExecute('SELECT listing_id FROM favorites WHERE user_id = ?', 'i', [$userId]);
    $result = $stmt->get_result();
    $favoriteIds = [];

    while ($row = $result->fetch_assoc()) {
        $favoriteIds[] = (int) $row['listing_id'];
    }

    return $favoriteIds;
}
```

Листинг 9.3 – Получение ID избранных объявлений

При рендеринге карточек объявлений система отмечает избранные элементы. Проверка выполняется с помощью функции in_array с строгим сравнением (true), что обеспечивает корректную работу с различными типами данных. Результат проверки передается в функцию renderListingCard в виде параметра is_favorite, который используется для добавления соответствующего CSS-класса или отображения иконки избранного. Такой подход позволяет пользователям быстро визуально идентифицировать сохраненные объявления среди результатов поиска или фильтрации.

```php
$isFavorite = isset($_SESSION['user_id']) && in_array((int) $listing['id'], $userFavorites, true);
$html .= renderListingCard($listing, [
    'is_favorite' => $isFavorite,
    'root_path' => '',
]);
```

Листинг 9.4 – Отметка избранного при рендеринге

Система избранного обеспечивает удобный способ сохранения и быстрого доступа к интересующим объявлениям. Персональный список избранного доступен только авторизованному пользователю и привязан к его учетной записи. Система не ограничивает количество объявлений в избранном, что позволяет пользователям сохранять любое количество вариантов для сравнения. Дата добавления (created_at) позволяет реализовать сортировку избранного по времени добавления, что может быть полезно для отслеживания недавно просмотренных объявлений. Интеграция с системой фильтрации обеспечивает seamless опыт – пользователи видят статус избранного непосредственно в результатах поиска.

## 10. Чат

Функционал чата позволяет пользователям обмениваться сообщениями в реальном времени, поддерживает отправку текстовых сообщений, изображений и видео.

Основная страница чата реализована в файле `chat.php`. Система проверяет авторизацию пользователя и загружает список бесед и сообщения. Логика работы чата включает несколько уровней: сначала проверяется авторизация пользователя, затем определяются параметры текущей беседы (ID собеседника, ID объявления, флаг поддержки). Система предотвращает создание беседы с самим собой, автоматически обнуляя selectedUserId, если он совпадает с ID текущего пользователя. Для режима поддержки реализован механизм блокировки беседы – администратор может «занять» беседу с пользователем, чтобы другие администраторы не могли вмешиваться. Если блокировка не может быть получена, система возвращает информацию о текущем владельце блокировки.

```php
if (!isset($_SESSION['user_id'])) {

}

$currentUserId = (int) $_SESSION['user_id'];
$selectedUserId = isset($_GET['user_id']) ? (int) $_GET['user_id'] : 0;
$selectedListingId = isset($_GET['listing_id']) ? (int) $_GET['listing_id'] : 0;
$selectedIsSupport = !empty($_GET['support']);
```

Листинг 10.1 – Инициализация чата

$partnerId = isset($_POST['user_id']) ? (int) $_POST['user_id'] : 0;

Листинг 10.2 – Обработка параметров сообщения

Для вложений система проверяет типы файлов, размер и количество:

```php
$allowedExtensions = ['jpg', 'jpeg', 'png', 'gif', 'webp', 'mp4', 'webm', 'mov'];

foreach ($validFileIndexes as $index) {
    $fileName = (string) ($fileNames[$index] ?? '');
    $fileTmpPath = (string) ($fileTmpNames[$index] ?? '');

Уведомления включают ID отправителя, ID получателя, флаг поддержки и ID сообщения.

ChatRealtimeNotifier::notifyUsers(

Это позволяет реализовать распределенную систему поддержки, где несколько администраторов могут обрабатывать запросы пользователей. Блокировка хранится в базе данных и имеет время жизни.

```php
if ($isSupport) {

Листинг 10.5 – Уведомление администраторов в режиме поддержки

Система чата обеспечивает полноценную коммуникацию между пользователями с поддержкой мультимедиа и реального времени. WebSocket-соединения позволяют мгновенно доставлять сообщения без необходимости периодического опроса сервера. Система также отслеживает статус прочтения сообщений – при открытии беседы сообщения автоматически помечаются как прочитанные, и отправителю отправляется уведомление о прочтении. Интеграция с системой объявлений позволяет привязывать беседы к конкретным объявлениям, что упрощает коммуникацию в контексте бронирования.

## 11. Админ-панель

Админ-панель предоставляет администраторам инструменты для управления верификацией пользователей, просмотра жалоб и модерации контента.

Основная страница админ-панели реализована в файле `admin.php`. Доступ к панели ограничен через класс `AdminAccess`, который проверяет роль пользователя и наличие прав администратора. Логика проверки прав реализована через метод requireAdmin(), который проверяет значение $_SESSION['user_role'] или выполняет запрос к базе данных для определения роли пользователя. Если пользователь не является администратором, он перенаправляется на главную страницу или страницу доступа запрещен. Такой подход обеспечивает безопасность административных функций и предотвращает несанкционированный доступ.

```php
require_once __DIR__ . '/bootstrap.php';
AdminAccess::requireAdmin();
```

Листинг 11.1 – Проверка прав администратора

Админ-панель включает два основных раздела: верификация и жалобы. Система использует сервис `AdminVerificationService` для получения статистики и заявок на верификацию. Статистика включает количество заявок в различных статусах (pending, approved, rejected) и общее количество верифицированных пользователей. Эти данные отображаются в виде бейджей на элементах интерфейса, позволяя администраторам быстро оценить текущую нагрузку на систему верификации. $mailer->Password = (string) SMTP_PASSWORD;

$mailer->setFrom($fromEmail, 'BelCouch');
$mailer->addAddress($recipient);

## 13. Верификация пользователей

Функционал верификации пользователей позволяет подтверждать личность пользователей через загрузку документа, что повышает доверие в сообществе.

Подача заявки на верификацию реализована через класс `SubmitVerificationRequestAction` в файле `app/Admin/Actions/SubmitVerificationRequestAction.php`. Логика подачи заявки включает строгую валидацию загружаемого файла: проверяется, что файл был успешно загружен (UPLOAD_ERR_OK), MIME-тип файла соответствует разрешенным (image/jpeg, image/png, image/webp), и размер файла не превышает 5 МБ. MIME-тип определяется через функцию mime_content_type, которая анализирует фактическое содержимое файла, а не полагается на расширение, что предотвращает обход проверок путем подмены расширения файла.

```php
$service = new AdminVerificationService();
$service->submitRequest((int) $_SESSION['user_id'], $_FILES['document_photo'] ?? []);
```

Листинг 13.1 – Подача заявки на верификацию

Метод `submitRequest` класса `AdminVerificationService` проверяет загружаемый файл. При успешной валидации система сначала отменяет все предыдущие заявки пользователя в статусе pending, устанавливая им статус rejected с комментарием 'Заявка заменена новой'. Это предотвращает накопление необработанных заявок и гарантирует, что администраторы видят только самую последнюю попытку верификации. Изображение документа сохраняется в базу данных как BLOB-объект с использованием метода send_long_data для корректной обработки больших бинарных данных. MIME-тип файла также сохраняется для корректного отображения при просмотре администратором.

```php
if (($file['error'] ?? UPLOAD_ERR_NO_FILE) !== UPLOAD_ERR_OK) {
    throw new Exception('Загрузите фото документа');
}

$allowed = ['image/jpeg', 'image/png', 'image/webp'];
$mime = mime_content_type($file['tmp_name']) ?: ($file['type'] ?? '');
if (!in_array($mime, $allowed, true)) {
    throw new Exception('Разрешены только JPG, PNG и WEBP');
}

if (($file['size'] ?? 0) > 5 * 1024 * 1024) {
    throw new Exception('Размер файла не должен превышать 5 МБ');
}
```

Листинг 13.2 – Валидация загружаемого документа

Изображение документа сохраняется в базу данных как BLOB. Использование BLOB вместо файловой системы обеспечивает централизованное хранение документов, упрощает резервное копирование и миграцию данных, а также предотвращает проблемы с правами доступа к файлам. Однако для больших систем может быть более эффективным хранение файлов в объектном хранилище (S3, MinIO) с сохранением только пути в базе данных. Текущая реализация использует прямое подключение к MySQL для отправки больших данных через send_long_data, что позволяет обойти ограничения на размер пакетов и корректно сохранить изображения любого размера в пределах установленного лимита.

```php
$imageData = file_get_contents($file['tmp_name']);
if ($imageData === false) {
    throw new Exception('Не удалось прочитать файл');
}

$this->db->prepareAndExecute('UPDATE verification_requests SET status = ?, admin_note = ?, reviewed_by = NULL, reviewed_at = NULL WHERE user_id = ? AND status = ?', 'ssis', ['rejected', 'Заявка заменена новой', $userId, 'pending']);

$mysqli = new mysqli(DB_HOST, DB_USER, DB_PASS, DB_NAME);
$mysqli->set_charset('utf8');
$stmt = $mysqli->prepare('INSERT INTO verification_requests (user_id, document_image, document_mime, status) VALUES (?, ?, ?, ?)');
$status = 'pending';
$null = null;
$stmt->bind_param('ibss', $userId, $null, $mime, $status);
$stmt->send_long_data(1, $imageData);
$stmt->execute();
```

Листинг 13.3 – Сохранение документа в базу данных

Модерация заявки выполняется администратором через метод `moderate`. Логика модерации включает проверку допустимости статуса (только 'approved' или 'rejected'), обновление записи заявки с установкой статуса, комментария администратора, ID модератора и времени рассмотрения. После успешного обновления заявки система автоматически обновляет поле is_verify в таблице users, устанавливая его в 1 для одобренных заявок и в 0 для отклоненных. Это обеспечивает немедленное отражение статуса верификации во всех частях системы. Изображение документа удаляется из базы данных после рассмотрения для освобождения места и обеспечения конфиденциальности.

```php
public function moderate(int $requestId, string $status, ?string $adminNote, int $adminId): void
{
    if (!in_array($status, ['approved', 'rejected'], true)) {
        throw new Exception('Недопустимый статус');
    }

    $this->db->prepareAndExecute(
        'UPDATE verification_requests
         SET status = ?, admin_note = ?, reviewed_by = ?, reviewed_at = NOW(), document_image = NULL, document_mime = NULL
         WHERE id = ?',
        'ssii',
        [$status, $note, $adminId, $requestId]
    );
    $this->db->prepareAndExecute('UPDATE users SET is_verify = ? WHERE id = ?', 'ii', [$status === 'approved' ? 1 : 0, (int) $request['user_id']]);
}
```

Листинг 13.4 – Модерация заявки на верификацию

Администратор может также вручную выдать или снять верификацию через метод `setManualVerification`. Этот метод используется для особых случаев, когда верификация не требует проверки документа (например, для доверенных пользователей, партнеров платформы или при технических проблемах). Метод напрямую обновляет поле is_verify в таблице users и создает запись в таблице verification_requests с документом NULL и статусом, соответствующим действию администратора. Комментарий администратора сохраняется для документирования причины ручного вмешательства. Все ручные верификации логируются и могут быть просмотрены в истории верификации пользователя.

```php
public function setManualVerification(int $userId, bool $isVerified, ?string $adminNote, int $adminId): void
{
    $this->db->prepareAndExecute(
        'UPDATE users SET is_verify = ? WHERE id = ?',
        'ii',
        [$isVerified ? 1 : 0, $userId]
    );

    $note = trim((string) $adminNote);
    if ($note === '') {
        $note = $isVerified ? 'Верификация выдана администратором вручную' : 'Верификация снята администратором вручную';
    }

    $this->db->prepareAndExecute(
        'INSERT INTO verification_requests (user_id, document_image, document_mime, status, admin_note, reviewed_by, reviewed_at)
         VALUES (?, NULL, NULL, ?, ?, ?, NOW())',
        'issi',
        [$userId, $isVerified ? 'approved' : 'rejected', $note, $adminId]
    );
}
```

Листинг 13.5 – Ручная верификация

Для просмотра загруженного документа используется метод `outputDocument`. Метод извлекает BLOB-данные из базы данных и отправляет их клиенту с правильным Content-Type заголовком на основе сохраненного MIME-типа. Устанавливаются заголовки Cache-Control с директивой no-store, чтобы предотвратить кэширование документов в браузере, что важно для конфиденциальных документов. Если документ не найден или был удален после рассмотрения, метод возвращает HTTP 404. Такой подход обеспечивает безопасный просмотр документов только авторизованными администраторами через веб-интерфейс без необходимости сохранения файлов на сервере.

```php
public function outputDocument(int $requestId): void
{
    $stmt = $this->db->prepareAndExecute('SELECT document_image, document_mime FROM verification_requests WHERE id = ?', 'i', [$requestId]);
    $stmt->store_result();
    if ($stmt->num_rows === 0) {
        http_response_code(404);
        exit;
    }

    $image = null;
    $mime = null;
    $stmt->bind_result($image, $mime);
    $stmt->fetch();
    if ($image === null) {
        http_response_code(404);
        exit;
    }

    header('Content-Type: ' . ($mime ?: 'application/octet-stream'));
    header('Cache-Control: no-store, no-cache, must-revalidate, max-age=0');
    echo $image;
    exit;
}
```

Листинг 13.6 – Вывод документа верификации

Система верификации обеспечивает подтверждение личности пользователей и повышает доверие в сообществе. Верифицированные пользователи получают визуальный индикатор (значок или бейдж) в интерфейсе, что позволяет другим пользователям быстро идентифицировать подтвержденные аккаунты. Система ограничивает изменение персональных данных для верифицированных пользователей, что предотвращает подмену личности после прохождения верификации. История всех заявок на верификации сохраняется, что позволяет отслеживать изменения статуса и выявлять паттерны поведения пользователей. В будущем может быть реализована автоматическая верификация через интеграцию с внешними сервисами (например, проверка по базе данных паспортов или интеграция с банковскими системами).

## 15. Телеграм-бот для подбора места путешествия

Телеграм-бот помогает пользователям подобрать город для путешествия на основе их интересов через интерактивный диалог.

Бот реализован на Python в файле `TelegramBot/main.py`. Используется библиотека `python-telegram-bot` для создания бота с обработкой состояний диалога. Логика бота построена на паттерне ConversationHandler, который управляет состоянием диалога пользователя. Бот имеет два основных состояния: CHOOSING (выбор типа отдыха) и CONFIRMATION (подтверждение рекомендации). Переход между состояниями происходит в зависимости от ответов пользователя. Такой подход позволяет сохранять контекст диалога и предоставлять пользователю возможность вернуться на предыдущий этап или изменить свой выбор.

Бот предоставляет пользователям выбор типа отдыха через клавиатуру. База рекомендаций представляет собой словарь, где ключами являются типы отдыха, а значениями – словари с информацией о городе и описанием. Клавиатура формируется как двумерный массив кнопок, где каждая строка содержит до двух кнопок для оптимального отображения на мобильных устройствах. Использование ReplyKeyboardMarkup с параметром resize_keyboard=true позволяет клавиатуре автоматически адаптироваться под размер экрана устройства пользователя. Такой подход обеспечивает удобный интерфейс без необходимости ввода текста вручную.

Листинг 15.1 – База рекомендаций и клавиатура выбора

При запуске бот приветствует пользователя и предлагает выбрать тип отдыха. Команда /start является точкой входа в диалог и переводит бота в состояние CHOOSING. Бот отправляет приветственное сообщение с клавиатурой выбора и возвращает состояние CHOOSING, что указывает ConversationHandler ожидать текстовый ввод от пользователя. Если пользователь отправляет команду /cancel в любой момент диалога, бот завершает conversation и удаляет клавиатуру, что позволяет пользователю прервать диалог в любой момент.

```python
async def start(update: Update, context: ContextTypes.DEFAULT_TYPE):
    await update.message.reply_text(
        "Привет! Я помогу подобрать город. Какой отдых вы хотите?",
        reply_markup=interest_markup
    )
    return CHOOSING
```

Листинг 15.2 – Обработка команды /start

После выбора типа отдыха бот предоставляет рекомендацию с описанием города. Обработчик handle_choice получает текстовый ввод пользователя и ищет соответствие в базе рекомендаций. Если ввод не соответствует ни одному из вариантов (например, пользователь ввел текст вручную вместо нажатия кнопки), бот возвращает сообщение об ошибке и повторно отображает клавиатуру выбора. При успешном совпадении бот сохраняет рекомендацию в context.user_data (специфическое хранилище данных пользователя в рамках сессии бота) и переводит диалог в состояние CONFIRMATION, отображая рекомендацию и клавиатуру подтверждения.

```python
async def handle_choice(update: Update, context: ContextTypes.DEFAULT_TYPE):
    user_choice = update.message.text.strip()
    logging.info(f"RAW INPUT: {repr(user_choice)}")

    recommendation = CITY_RECOMMENDATIONS.get(user_choice)

    if not recommendation:
        await update.message.reply_text(
            "Я не распознал вариант. Пожалуйста, нажмите кнопку ниже.",
            reply_markup=interest_markup
        )
        return CHOOSING

    context.user_data['recommendation'] = recommendation

    await update.message.reply_text(
        f"Подходит город: {recommendation['город']}\n\n"
        f"{recommendation['описание']}\n\n"
        f"Вас устраивает?",
        reply_markup=confirmation_markup
    )

    return CONFIRMATION
```

Листинг 15.3 – Обработка выбора типа отдыха

Пользователь может подтвердить или отклонить рекомендацию. В состоянии CONFIRMATION бот ожидает ответ «Да» или «Другое». При подтверждении бот формирует inline-клавиатуру с кнопкой «Перейти на сайт» (ссылка на belcouch.by) и кнопкой «Выбрать заново» (callback data для возврата в начало). Inline-клавиатура отличается от reply-клавиатуры тем, что она привязана к конкретному сообщению и не заменяет основную клавиатуру. При выборе «Другое» бот возвращается в состояние CHOOSING и повторно отображает клавиатуру выбора типа отдыха. Такой циклический процесс позволяет пользователю исследовать различные варианты до нахождения подходящего.

```python
async def handle_confirmation(update: Update, context: ContextTypes.DEFAULT_TYPE):
    answer = update.message.text

    if answer == "Да":
        recommendation = context.user_data.get('recommendation')

        keyboard = [
            [InlineKeyboardButton("Перейти на сайт", url="https://belcouch.by")],
            [InlineKeyboardButton("Выбрать заново", callback_data="return_to_start")]
        ]

        await update.message.reply_text(
            f"Отлично!\n\n{recommendation['город']}\n{recommendation['описание']}",
            reply_markup=InlineKeyboardMarkup(keyboard)
        )
        return CONFIRMATION

    elif answer == "Другое":
        await update.message.reply_text(
            "Попробуем снова:",
            reply_markup=interest_markup
        )
        return CHOOSING
```

Листинг 15.4 – Обработка подтверждения рекомендации

Бот использует ConversationHandler для управления состояниями диалога. ConversationHandler настраивается с точкой входа (entry_points) – команда /start, картой состояний (states) с соответствующими обработчиками, и fallback-обработчиками для команд выхода из диалога. Для состояния CONFIRMATION настроены два типа обработчиков: MessageHandler для текстовых ответов и CallbackQueryHandler для inline-кнопок. Это позволяет боту обрабатывать как текстовые вводы, так и нажатия на кнопки в одном состоянии. При завершении диалога (успешном или через команду /cancel) бот удаляет пользовательские данные и сбрасывает состояние, что обеспечивает чистоту данных для новых диалогов.

```python
conv_handler = ConversationHandler(
    entry_points=[CommandHandler('start', start)],
    states={
        CHOOSING: [
            MessageHandler(filters.TEXT & ~filters.COMMAND, handle_choice),
        ],
        CONFIRMATION: [
            MessageHandler(filters.TEXT & ~filters.COMMAND, handle_confirmation),
            CallbackQueryHandler(button_callback, pattern="^return_to_start$")
        ],
    },
    fallbacks=[CommandHandler('cancel', cancel)],
)
```

Листинг 15.5 – Настройка обработчика состояний

Телеграм-бот обеспечивает удобный интерактивный способ подбора места путешествия на основе интересов пользователя с возможностью перехода на сайт для бронирования. Бот работает асинхронно, используя async/await синтаксис Python, что позволяет обрабатывать множество пользователей одновременно без блокировки. Логирование настроено для отслеживания всех взаимодействий с ботом, что помогает в отладке и анализе использования. Бот может быть легко расширен дополнительными функциями, такими как сохранение предпочтений пользователя, интеграция с API платформы для прямого бронирования из Telegram, или добавление более сложной логики рекомендаций на основе истории пользователя.
